### 3. Focus states extremely thin (a11y CRITICAL) — ✅ FIXED 2026-05-03

Implemented Option A (global CSS rule) in both files:
- `landing.html:26-33`
- `room-booking.html:18-26`

Rule applied: `button/a/input/select/textarea:focus-visible { outline: 2px solid #2178cf; outline-offset: 2px }`. Keyboard-only (`:focus-visible`), uses primary blue, no impact on mouse users.

**Status numbers (pre-fix):**
| File | buttons | `focus:`/`focus-visible:` rules |
|---|---|---|
| `landing.html` | ~107 | 7 |
| `room-booking.html` | 41 | 0 |

**Why this matters (in plain terms):**
When a user navigates with the keyboard (`Tab` key), the browser highlights whichever element is currently "focused" so they know where they are. The browser's default highlight is a thin outline, but most modern UIs override it with `outline: none` or use Tailwind's reset — which kills the indicator. Result: keyboard users (including power users, screen-reader users, anyone with motor impairment) lose their place and can't tell which button they're about to click.

**Three implementation options, ordered by impact-to-effort ratio:**

**Option A — Global CSS rule (recommended, 1 line per file)**
Add to the `<style>` block in each HTML head:
```css
button:focus-visible,
a:focus-visible,
input:focus-visible,
select:focus-visible,
textarea:focus-visible {
  outline: 2px solid #2178cf;
  outline-offset: 2px;
}
```
- Pros: one place, covers everything, uses your existing primary blue (`#2178cf`).
- Cons: visual style is uniform; can't easily differentiate button kinds.
- `:focus-visible` (not `:focus`) only shows on keyboard nav, not on mouse click — important for not annoying mouse users.

**Option B — Tailwind utility on button base (per-component)**
Add `focus-visible:ring-2 focus-visible:ring-[#2178cf] focus-visible:ring-offset-2 focus-visible:outline-none` to each button. Tedious for 148 buttons unless you have a base class.
- Pros: per-button control.
- Cons: lots of editing.

**Option C — Define a reusable utility in `<style>`**
```css
.focus-ring:focus-visible {
  outline: 2px solid #2178cf;
  outline-offset: 2px;
}
```
Then add `class="... focus-ring"` to interactive elements. Middle ground.

**My recommendation:** Option A. One CSS block, both files, done. Can be undone or scoped later if you want per-component theming.

**Risk/side-effect:** none. `:focus-visible` is supported in all evergreen browsers (Chrome 86+, Firefox 85+, Safari 15.4+). Older Safari just falls back to no indicator (same as today).

### 4. `prefers-reduced-motion` not respected — ✅ FIXED 2026-05-03

Wildcard reduce-motion block added in both files:
- `landing.html:36-45`
- `room-booking.html:29-38`

Sets `animation-duration`/`transition-duration` to `0.01ms !important` and `scroll-behavior: auto` for users with the OS-level reduced-motion setting on. Sidebar collapse and accordion rotates now snap (intended) for those users.

**What this is:**
A user OS-level setting: macOS *System Settings → Accessibility → Display → Reduce motion*; Windows *Settings → Accessibility → Visual effects → Animation effects off*; iOS/Android equivalents. When toggled on, the browser exposes a CSS media query `prefers-reduced-motion: reduce` that pages can read.

**Who turns it on:**
- People with vestibular disorders (motion sickness, vertigo) — slide/zoom animations literally make them nauseated
- People with migraine sensitivity to motion
- Users on low-power devices wanting to save battery
- Some screen-reader users who find animation distracting

Estimated 1–3% of users have this enabled. Small fraction, but for them it's a hard accessibility blocker.

**What in your project would be affected:**
Looking at the current files, the actual motion footprint is small:
- `room-booking.html`: sidebar collapse (`width 0.2s ease`), label fade (`opacity 0.15s`), accordion icon rotate (`transition-transform`)
- `landing.html`: tab/dropdown transitions, hover color fades, accordion rotates

None are aggressive — no parallax, no big slides, no auto-playing carousels. So the *blast radius* of NOT fixing this is low. But the *cost* of fixing it is also tiny (one CSS block).

**Suggested fix:**
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```
- Add to the `<style>` block in each HTML head (same place as the other rules).
- The wildcard selector + `!important` is the standard pattern from a11y guides — it kills *all* transitions/animations for users who opt in. This is what you want; specific overrides are rarely worth the maintenance.

**Side-effect to know about:** the sidebar collapse won't slide smoothly for reduced-motion users — it'll snap. That's the *intended* behavior; they asked for it.

**My recommendation:** add it. Cost is one block of CSS, benefit is genuine for affected users, and it doesn't change anything for the 97%+ who don't have the OS setting on.
